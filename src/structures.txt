### Structure pour l'execution des commandes (chargées dans commands):
Il existe 2 facons d'executer les données selon si les données sont enrgistrées ou non.
    - executeUnregisterdCommand     // Fabriquer les données à la volée avant d'executer la commande
    - executeRegisteredCommand      // Les données sont issues du catalogue ou des fichiers de commandes
Le dispatcheur pour l'execution des commandes utilise la variable 'commandHandler' quel que soit la méthode,
les données sont stockées sous forme de list de paramétres (string) générique 'payload' et d'une string 'additionnalPayload'.
commandHandler décrit à la fois la maniere d'extraire et de former les données et la fonction a executer.
    Ex: 3 pour transmettre un signal infrarouge IR avec les données issues de 'decode_results'

struct commandData2
{
  commandHandlers commandHandler;           // Défini le type de données contenus dans commandPayloads (Ex: 3 pour les données IR 'decode_results') 
  std::string requestType;                  // Défini comment s'utilise le dispositif BLE pour la commande "WRITE" : écriture BLE, "READ" : lecture BLE.
  std::string attributs;                    // Attributs pour les autorisations d'ecriture (effacement) "w" autorise l'effacement (en Flash). (Non géré actuellement)
  std::list<std::string> commandPayloads;   // Contient les données propre à la commande (son type de données est décrit par commandHandler)
};

### Structure json pur le transport et l'execution de taches json :
les taches peuvent être être transmise depuis le dispositif BLE sur 3 canaux BLE.
    - CHARACTERISTIC_COMMAND2_UUID          // execution de taches complexe (- rapide).
    - CHARACTERISTIC_EXECUTE_COMMAND_UUID   // execution d'une commande (+ rapide).
    - CHARACTERISTIC_DELETE_COMMAND_UUID    // suppression d'une commande (+ rapide).
A noter que certaine valeur transmises peuvent être null (ou empty), dans ce cas le programme peut leurs attribuer une valeur par défaut.
--> CHARACTERISTIC_COMMAND2_UUID:
{
"taskType": "EXECUTE",
"commandName": "IR_4_0xA90_1",
"directData": {
    "protocol": "3",
    "data": "238"
    },
"addPayload": {
    "frequency": "36",
    "toggleMask": "0x8000",
    "repeat": "2",
    "raw": "0"
    }
}

--> CHARACTERISTIC_EXECUTE_COMMAND_UUID:
Attention : Seul "IR_MCE_POWER" est transmis dans le message BLE!
{"taskType": "EXECUTE", "taskPayload": {"commandName": "IR_MCE_POWER"}}

--> CHARACTERISTIC_DELETE_COMMAND_UUID:
Attention : Seul "IR_MCE_POWER" est transmis dans le message BLE!
{"taskType": "DELETE", "taskPayload": {"commandName": "IR_MCE_POWER"}}


Structure json "Commands_json_bootloader" et "Commands_json" :
Ceci est le format json utilisé pour décrire une commande,
il est utilisé pour les commandes issues du bootloader ou des fichiers de commandes stockés en Flash.
{
   "IR_SONY_POWER": {                   //Clé unique pour le nom de la commande.
    "commandHandler": "3",              //"3" = Commande d'emission infrarouge
    "requestType": "WRITE",             //"WRITE" : commande utilisable en écriture depuis un dispositif BLE, "READ" : commande utilisable en lecture.
    "attributs": "w",                   //"w" : l'attribus "w" autorise l'effacement de la commande (en Flash). (Non géré actuellement)
    "commandPayloads": [                //Contient les données utiles pour l'envoi d'une commande (Le contenu dépendant du type de commande "commandHandler", pour infrarouge par exemple)
        "900",
        "0xA90",
        "12",
        "2"
    ]
    },
    "IR_MCE_POWER": {
    "commandHandler": "3",
    "requestType": "WRITE",
    "attributs": "w",
    "commandPayloads": [
        "901",
        "0xC800F040CLL",
        "36",
        "0x8000",
        "true"
    ]
    },
};

Structure json pour lecture du catalogue des commandes via la requette ble READ :
Ce format ressemble au précédent mais il est différent et ne comprends pas de Payloads.
// Exemple : {"command": "IR_CAPTURE", "status": "ERROR_READING_FILE", "requestType": "WRITE", "attributs": "w", "commandHandler": "3"}
le status "OK" ou "ERROR_READING_FILE" est utilisé pour signaler un message ou fichier de commande invalide.

Header encapsulé dans le 1er paquet (taille limite : 20 Caractères Maxi) :
    Format: "HEADER:nombres de paquets, taile des paquets"
    Exemple: "HEADER:700;20"

Structure d'un message en réponse à une requette READ pour la lecture d'une caractéristic :
La mise en paquet est controlé en fonction du nom de la requette READ.
	Exemple :
	LAST_CAPTURE 	-> (transmission par paquets)
	READ_FREE_HEAP 	-> (transmission simple)
